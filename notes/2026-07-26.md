# Notes, 26 July (ran into the 27th)

Everything measured on this machine against exact brute-force ground truth. Projections are
marked as projections.

Short version: went from a prototype with no real ANN numbers to a flat-cell index that beats
faiss at 100k on R@10, throughput, build and delete, with a list of where it still loses.

## Starting point

The repo described a Hopfield router, deep attractor trees and NSW graphs in the leaves, and had
no ANN recall measurement at all; the benchmarks counted MS MARCO qrel hits, which mostly measures
the embedding model. The first ground-truth run showed:

| What the docs said | What I measured |
|---|---|
| 98% recall | qrel hit rate. ANN R@10 was 0.9648 and didn't move with more search |
| 10x faster build than faiss | faiss IVFFlat built it 10x faster than me (0.9 s vs 9.6 s) |
| same or better memory | 2.1x HNSW; the boundary copies didn't show in `stats()` |
| continuous Hopfield router | one softmax over centroid cosines, no iteration: IVF probe selection |

Recall that doesn't move with more search means the scoring is the limit. Cause: the quantizer did
`x * 127.0` on unit vectors. At d=384 a component's std is 0.051, so only 66 of 255 int8 levels
were used (~6 bits), and there was no full-precision rerank.

## Literature

Read before writing any new code (details in the plan). SPANN, SPFresh, Quake, RaBitQ, SOAR, DARTH
and the Big-ANN streaming track between them cover almost everything I'd thought of as new. Quake
in particular already does in-memory adaptive maintenance and adaptive probing. The Hopfield
framing is gone.

## What I built

| Part | File | |
|---|---|---|
| flat-cell core | `src/index_v2.rs` | one arena, u32 cell offsets, AVX2 kernels, O(1) delete, 4 scan/rerank modes |
| binary codes | `src/rabitq.rs` | FHT rotation, sign bits, POPCNT Hamming, codes can be truncated |
| centroid graph | `src/centroid_index.rs` | HNSW over centroids |

| save/load | `src/persist.rs` | little-endian format, derived state rebuilt on load |
| ground truth | `bench/groundtruth.py` | exact k-NN, streamed (fine at 1M+) |
| ANN bench | `bench/run_ann_recall.py` | recall vs QPS against 5 faiss configs |
| churn bench | `bench/run_churn.py` | |
| routability | `bench/routability_study.py` | can a learned ranker pick better cells |
| tests | `tests/test_index_v2.py` | 30 invariant checks |

```text
  centroids (f32 scan, or binary shortlist then exact re-order, or the graph)
       |  adaptive probing with a reachability bound
       v
  cells: Vec<u32> offsets into one arena
       |  flat SIMD scan of 1-bit codes (64 B/vector), no graph in the cell
       v
  rerank the top k*rf against per-dimension SQ8 (384 B/vector)
```

* **No graph in the cell.** Flat int8 beats NSW (ef=100) up to ~10k vectors per cell, and NSW
  adjacency at M=64 is 544 B/node against 384 B of vector. It would also rule out O(1) delete.
* **O(1) delete.** `swap_remove` plus the arena free list. 0.9 us at 100k, 1.1 us at 1M.
* **Exact centroids** from `(sum, count)` instead of the old `0.9*old + 0.1*new` EMA.
* **Build flags:** `target-cpu=native`, fat LTO, one codegen unit. Without them the AVX2 kernels
  don't inline.

## The two results everything else follows from

**Quantization costs no recall with a rerank.** int8 and f32 recall identical at every nprobe;
binary at rf=8 gets 0.9942 vs 0.9943 for int8.

**The scan is bandwidth bound.**

| nprobe | v2-f32 | v2-i8 | speedup | byte ratio |
|---|---|---|---|---|
| 32 | 1,896 | 6,424 | 3.4x | 4x |
| 128 | 484 | 1,910 | 3.9x | 4x |

~25.6 GB/s at nprobe=32. So speed is a bytes-per-query problem, and quantization is worth much
more to a scan than to a graph.

## Didn't work

| Idea | Result | Why |
|---|---|---|
| learned cell ranker | GBM over 8 features, AUC 0.9715 vs 0.9664 for cosine, but 37 probes vs 32 in practice | cosine already uses what's known at query time |
| reachability-bound ranking | 42-45 probes vs 32 | max radius is set by one outlier |
| sub-centroids | +2.4 points R@10 at np=8, only 1.2-1.3x on bytes | extra keys cost more than they save |
| kNN-graph refinement of the partition | fragmentation 3.50 -> 3.21 cells, recall unchanged | boundaries are inherent to Voronoi cells |
| redundant assignment | never pays; more nprobe beats copying at every cell count | only nearly even at ~8 cells |
| 256-bit codes | R@100 0.9923 -> 0.9479 | the pool needs full resolution to keep 100 neighbours |
| fine cells with quantization | 3,000 cells: 1.86 -> 4.40 ms | fine cells win 8x in f32, but with 64 B codes the cost moves to routing |
| residual binary codes | 0.9733 vs 0.9789 at rf=8 | |
| per-vector int8 scale | MRR 0.9900 vs 0.9925 | global scale only wastes 0.77 bits |
| residual SQ8 rerank | MRR 0.9938 vs 0.9950 | residual ranges are wider (0.4343 vs 0.4102) |
| centroid graph below 4096 cells | caps recall | greedy search can't enumerate every cell |
| centroid graph at 5,000 cells (1M) | R@10 0.9080 vs 0.9332 flat | beam `ef = max(2*nprobe, 64)` is too narrow; retest |

## What did work

Per-dimension affine SQ8 (like faiss `QT_8bit`) instead of one global scale. Same 8 bits, ~3 KB of
shared metadata, nothing extra per vector:

| | R@10 | R@100 | MRR |
|---|---|---|---|
| global scale | 0.9948 | 0.9923 | 0.9935 |
| per dimension | 0.9962 | 0.9948 | 0.9943 |

faiss wasn't spending more bits than me, it was spending them better. Embedding dimensions have
very different variances, and one global scale wastes range on most of them.

## 100k, best recall

N = 99,000, k=100, 1,000 queries, 16 threads for every engine, best of 7.

| system | R@10 | R@100 | MRR | lat ms | p99 | qps | build | RSS MB | delete |
|---|---|---|---|---|---|---|---|---|---|
| v2 (SQ8 rerank) | 0.9962 | 0.9948 | 0.9943 | 2.639 | 3.79 | 4,046 | 2.0 s | 64.7 | 0.9 us |
| faiss-hnsw f32 | 1.0000 | 0.9971 | 1.0000 | 1.079 | 1.48 | 3,958 | 22.9 s | 171.4 | none |
| faiss-ivf f32 | 0.9942 | 0.9877 | 0.9990 | 3.700 | 4.79 | 714 | 1.1 s | 197.1 | O(N) |
| faiss-hnsw SQ8 | 0.9954 | 0.9931 | 0.9965 | 3.077 | 4.31 | 2,893 | 41.1 s | 62.1 | none |
| faiss-ivf SQ8 | 0.9956 | 0.9948 | 0.9980 | 36.2 | 40.4 | 198 | 1.4 s | 54.3 | O(N) |

Ahead on R@10 and throughput, 11-20x faster build, the only one with delete. Behind on MRR,
single-query latency against f32 HNSW (2.6 vs 1.1 ms), and slightly on memory against the SQ8
variants.

On fairness of the rerank: mine is two-stage (binary scan, then SQ8 on the top k*rf); the faiss
SQ8 configs score every probed vector with SQ8 directly. Final precision is SQ8 in both, so
there's no precision edge. They're more thorough, which is also why their MRR is higher and why
I'm faster.

Quantization helps one design and hurts the other:

| | f32 | quantized | change |
|---|---|---|---|
| faiss-hnsw ef=16 | 36,008 | 27,375 (SQ8) | -24% |
| faiss-hnsw ef=32 | 20,893 | 16,700 (SQ8) | -20% |
| v2 (binary + rerank) | ~1,900 | ~21,900 | about 11x |

Compressing an HNSW node doesn't remove any dependent memory round trips, it just adds decode
work to each. A bandwidth-bound scan gets the full benefit.

## Scaling

Right now the query side is worse than HNSW asymptotically:

| | |
|---|---|
| HNSW | O(ef log N) |
| v2 with sqrt(N) cells | O(nprobe sqrt(N)) |
| v2 with fixed cell size and graph routing | O(log N) |

At nprobe=32 it scans 10,080 vectors at 100k and 32,000 at 1M: 3.2x for 10x the data, which is
sqrt(10). Build too: flat k-means with sqrt(N) cells is O(N^1.5 d); 2.0 s at 100k, 74 s at 1M
with 5,000 cells.

Projection, assuming fixed cells, graph routing and hierarchical build. Bytes per query stay
around 2.5 MB; HNSW's grow slowly and its effective bandwidth drops as the graph leaves cache.

| N | v2 | HNSW | |
|---|---|---|---|
| 100k | 100 us | 46 us | HNSW 2.2x |
| 1M | 100 us | 67 us | HNSW 1.5x |
| 10M | 100 us | 104 us | about even |
| 100M | 100 us | 183 us | v2 1.8x |
| 1B | 100 us | 271 us | v2 2.7x |

The weak assumption is that nprobe stays constant as the cell count grows. If it grows even like
log N the crossover moves right. That's the first thing to check.

Which advantages grow with N:

| | grows with N? |
|---|---|
| delete (O(1) vs none or rebuild) | yes; a 1B rebuild takes hours |
| maintenance (local split vs global rebuild) | yes |
| recall under churn | yes |
| build (11-20x now, HNSW at 1B is days) | yes |
| query | no, against me for now (sqrt(N) vs log N) |
| memory | constant, ~1.4x |

So the real advantages are on the update side. Any query advantage comes late (~10M) and depends
on fixes I haven't validated.

## Automatic sizing

`recommend()` encodes the measured crossovers; `autotune()` splits and merges toward the target
and switches graph routing on or off. Growing 10k -> 60k:

```text
n=10,000  cells 100 -> 101   mean cell 100 ->  99   sqrt(N)=100
n=30,000  cells 115 -> 138   mean cell 261 -> 217   sqrt(N)=173
n=60,000  cells 170 -> 179   mean cell 353 -> 335   sqrt(N)=244
```

Works incrementally and never retrains the quantizer (faiss IVF would have to). One pass only
splits cells outside the band, so it moves toward sqrt(N) without reaching it. Needs a lower
`split_ratio` or several passes.

## Where a tree comes back

Not as the router over data. But at 1B with 512-vector cells there are 2M centroids, and routing
over them needs some structure:

* flat binary scan: 2M x 64 B = 128 MB per query, no
* HNSW over centroids: built, underperforming so far
* a 2-level centroid tree (~1,400 coarse -> 2M fine): depth 2, so the error is p^2, not p^d, and
  coarse nodes are cheap enough to probe several

The hierarchy idea from June was right, it was just at the wrong level. Over data vectors it
compounds error (98% -> 31.5%). Over centroids at depth 2 it's SPANN's hierarchical balanced
clustering, and above ~100M it's close to required.
